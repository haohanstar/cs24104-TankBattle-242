## 2. 分支模型（先理解再动手）

```
main        ──●────────●────────●──   交付/答辩用的稳定版；只有组长在交付前合并
                \      /        /
develop     ────●────●────────●────   大家的成果汇合到这里；只通过 PR 合入
                  \  /        /
feature/张三  ────●●        /          每个人自己的分支；日常提交都在这里
feature/李四  ───────●●────
```

**三条铁律：**

1. 任何人**不直接 commit / push 到 `main`**。
2. **不直接 push 到 `develop`**，一律走 Pull Request（PR）。
3. 自己的代码只在 `feature/<姓名>-<模块>` 上提交。

> 每次 push 前必须完成第 6.5 节的「推送前自检」；铁律靠自觉执行，误推后按第 8.7 节恢复。

## 5. 接口契约（写代码前必须先核对）

### 5.1 唯一依据

- 地图/地形/碰撞：`docs/map-spec.md`（当前 v0.1，W11 冻结 v1.0）
- 地图 JSON 字段：`maps/schema/map.schema.json`
- 项目说明：`README.md`

**这三份文件是唯一标准。**代码、注释、AI 输出与它们不一致时，以文件为准。

### 5.2 地图元数据（C/E 联机与展示必须对齐）

| 字段 | 类型 | 说明 |
|---|---|---|
| `map_id` | string | 唯一标识，匹配 `^[a-z0-9_]+$`，如 `arena_01` |
| `name` | string | 显示名 |
| `version` | int | 地图版本，联机比对 |
| `seed` | int | 生成种子；手工图为 0 |
| `difficulty` | enum | `easy` / `normal` / `hard` |
| `hash` | string | 静态地图规范化 JSON 的 SHA-256 前 16 位 |
| `size` | {w,h} | 默认 26×26 |

`tiles` 枚举：`empty` / `brick` / `steel` / `water` / `ice` / `grass` / `base`。
schema 设置了 `additionalProperties: false`，**不要临时加字段**。

### 5.3 `MapService` 接口（B 提供，其他模块调用）

| 方法 | 返回 | 调用方 | 说明 |
|---|---|---|---|
| `load(mapId, version)` | `TileMap` | B / C | 加载并缓存地图 |
| `isBlocked(rect, mover)` | `bool` | A | 坦克 AABB 与地形碰撞 |
| `terrainAt(cell)` | `TerrainEffect` | A / D | 摩擦、遮挡、可通行 |
| `hitBullet(cell, power)` | `BulletHit` | A | 子弹命中；返回是否破坏 |
| `spawnPoints()` | `List<Cell>` | A / C | 出生点 |
| `freeCells()` | `List<Cell>` | D | 可放置道具的空格 |
| `metadata()` | `MapMetadata` | C / E | 地图名/难度/hash |

**事件：** `TileDestroyed(cell, type, byPlayer)` → C 广播为 `MAP_STATE`，回放保存"初始地图 + 事件序列"。

### 5.4 模块边界（谁负责什么，禁止越界）

| 模块 | 只负责 | 明确不负责 | 与别人怎么交互 |
|---|---|---|---|
| **A 战斗引擎** | 坦克移动/转向、坦克-坦克、坦克-子弹、武器与弹道 | 不自己写地形判断、不直接读 `.tmx` | 地形碰撞一律调 `isBlocked` / `terrainAt` / `hitBullet` |
| **B 地图系统** | 地图加载、地形渲染、地形查询、编辑器、AI 地图生成 | 不反向调用 A/C/D/E 的业务逻辑、不改战斗状态 | 只提供查询和事件 |
| **C 对战房间** | 房间、状态同步、观战、录像回放、协议 | 不直接改地图内容、不绕过 B 读地图 | 用 `map_id/version/hash` 对齐两端地图，广播 `MAP_STATE` |
| **D 道具升级** | 道具生成/拾取/效果、升级树 | 不修改地形、不直接改坦克核心属性 | 用 `freeCells()` 和事件；升级效果与 A 协商 |
| **E 大厅战队** | 登录、好友、组队、战队、排行榜、锦标赛 | 不直连游戏内逻辑、不写地图数据 | 通过 C 的 API/WS；地图信息只读 |

### 5.5 接口变更流程（不允许"先改了再说"）

1. 在群里发「接口变更提案」：旧签名 → 新签名、为什么改、影响哪些模块、怎么迁移、最晚什么时候完成。
2. 组长 + 所有受影响模块确认。
3. 更新 `docs/map-spec.md` 版本（如 v0.1 → v0.2）和 `maps/schema/map.schema.json`。
4. 受影响模块在同一个迭代内适配，`develop` 合并前必须能构建。
5. 只加字段/方法可以先做，但**必须同步文档**；删改既有签名必须先确认。

### 5.6 让 AI 先做的接口检查清单

把下面这段连同本文件发给 AI，让它逐条回答：

```text
请对照 docs/map-spec.md 和 maps/schema/map.schema.json，检查我这次改动：
1. 是否新增/修改了 MapService 的 7 个方法？签名是否一致？
2. 是否新增/修改了地图元数据字段？是否违反 schema 的 additionalProperties=false？
3. 我调用别人接口时，方法名、参数、返回值是否与接口表一致？
4. 我是否越界实现了别人模块的职责（见 5.4 表）？
5. 是否需要更新 map-spec.md / schema / 版本号？
6. 如果发现不一致，先列冲突点并停止，不要自行改接口。
```

## 6. 日常开发与提交（每个成员都按这个来）

### 6.1 开始干活前：同步 develop

```bash
git checkout develop
git pull origin develop
git checkout feature/<你的分支>
git merge origin/develop        # 把最新集成版合进来，减少后面冲突
```

> **每次开工都要做**：这样既能拿到最新代码，也能拿到最新版《协作规范》（组员的任务提示会让 AI 读这份文档）。

### 6.2 写代码 → 小步提交

每完成一个小功能就提交，不要攒一整天：

```bash
git status                      # 先看改了什么
git add <文件或目录>
git commit -m "feat(battle): 坦克八方向移动与碰撞查询"
```

提交信息格式：`类型(模块): 中文说明`

| 类型 | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 文档 |
| `test` | 测试 |
| `refactor` | 重构（不改行为） |
| `chore` | 构建/配置/杂项 |

示例：

- `feat(map): 加载 Tiled 正交地图与三层图层`
- `fix(item): 修复冰面拾取道具后重复触发`
- `test(room): 增加房间加入/离开的单元测试`
- `docs(map): 地图规范补充冰面摩擦系数`

### 6.3 推送自己的分支

```bash
git push -u origin feature/<你的分支>
```

第一次推会要求登录 GitHub：浏览器授权，或在提示密码处粘贴 **Personal Access Token**（Settings → Developer settings → Personal access tokens，勾选 `repo`）。不要用账号密码。

### 6.4 什么不要提交

- `build/`、`.gradle/`、`node_modules/`、`*.class`、`*.jar` 等构建产物
- `.idea/`、`.vscode/` 等 IDE 配置（除非团队约定共享）
- 日志、临时文件、`__pycache__`、压缩包
- 个人实验报告成稿与报告生成脚本（`report/`、`src/build_report*.py`、`src/export_pdf*.py`、`src/report_helpers.py` 等，已在 `.gitignore`）
- 第三方库、密钥、token、密码
- 大于 10MB 的单个文件（素材先放网盘/Release，仓库里只放必要的小文件）

### 6.5 推送前自检（强制）

每次 `git push` 之前，按顺序执行并把结果贴出来：

```bash
git branch --show-current   # 必须是 feature/xxx
git status                  # 确认改了哪些文件
git push -u origin HEAD     # 用 HEAD，避免手打分支名打错
```

**正确示例**：

```bash
$ git branch --show-current
feature/yaoyuxuan-battle
$ git push -u origin HEAD
```

**错误示例（禁止）**：

```bash
# ❌ 当前在 develop 上
$ git branch --show-current
develop
$ git push origin develop          # 禁止：直接改集成版

# ❌ 手打分支名打错，推到了共享分支
$ git push origin main             # 禁止

# ❌ 强推覆盖别人的提交
$ git push --force                 # 禁止
```

> AI 执行 push 时也必须先跑 `git branch --show-current`；分支名不以 `feature/` 开头就停止，先问组员，不要自行切换或强推。

## 8. 冲突（"误差"）怎么处理

### 8.1 什么时候会冲突

两个人改了**同一个文件的同一片区域**，Git 无法自动决定保留谁，就会产生冲突。改不同文件、不同区域时 Git 会自动合并。

### 8.2 本地解决冲突（推荐）

```bash
git checkout feature/<你的分支>
git fetch origin
git merge origin/develop
```

冲突文件里会出现：

```text
<<<<<<< HEAD
你本地的内容
=======
develop 上的内容
>>>>>>> origin/develop
```

处理步骤：

1. 打开冲突文件，**保留正确的内容，删掉 `<<<<<<<`、`=======`、`>>>>>>>` 三行标记**；
2. 不要整段删掉别人的功能，不确定就停下来问；
3. 改完运行构建/测试；
4. 提交并推送：

```bash
git add <冲突文件>
git commit -m "merge: 同步 develop 并解决冲突"
git push
```

VS Code / IntelliJ 都有可视化冲突解决界面，可以点「接受当前 / 接受传入 / 两者都保留」，比手改安全。

### 8.3 在 GitHub 网页解决

PR 页面提示 **This branch has conflicts** 时，可以点 **Resolve conflicts** 在线编辑；冲突复杂时建议回本地解决。

### 8.4 push 被拒绝（non-fast-forward）

说明远端有你本地没有的提交，先合并再推：

```bash
git pull --no-rebase origin <你推的分支>
# 或 git fetch origin && git merge origin/<分支>
git push
```

### 8.5 合坏了想回退

```bash
git log --oneline           # 找到那次提交
git revert <提交号>         # 生成一个反向提交，安全，不改历史
```

### 8.6 绝对禁止

- **不要 `git push -f` / `--force` 到共享分支**（会覆盖别人提交）。
- 不要用 `git reset --hard` 处理共享分支。
- 不要为了"看起来干净"删除别人的提交。

> 唯一的例外是 2026-11-07 组长清理历史那一次：`main`、`develop`、`feature/yaoshuai-map` 三个分支由组长统一强推，组员**不要模仿**，也不要自己再强推任何分支。

### 8.7 误推到 main / develop 怎么办

1. **不要** `git reset --hard`，也不要 `push -f` 去"修正"；
2. 立即在群里通知组长，说明误推的提交号；
3. 由组长确认后，用 `git revert <提交号>` 生成反向提交（安全，不改写历史）；
4. 如果你只是 push 了自己的 `feature/` 分支，不需要处理——那本来就是正确位置。

## 11. 常见问题排查

| 现象 | 原因 | 处理 |
|---|---|---|
| `Permission denied` / 403 | 没接受邀请或没登录 | 接受 Collaborators 邀请，重新登录 GitHub |
| `Could not read Username` | 没配置凭据 | 用浏览器授权，或把 PAT 当密码输入 |
| 连接 GitHub 超时 | 网络受限 | 开代理；本机配置 `git config http.proxy http://127.0.0.1:<端口>`（只写自己机器） |
| `non-fast-forward` | 远端有新提交 | 先 `git pull --no-rebase` 合并再推 |
| PR 显示冲突 | 与 develop 改了同一处 | 本地 merge develop，按第 8 节解决 |
| 误把文件提交到 develop | 忘了建分支 | `git checkout -b feature/xxx` 保存当前提交，再把本地 develop 重置到 `origin/develop` |
| 提交了不该提交的文件 | 没看 `git status` | `git rm --cached <文件>`，加入 `.gitignore`，再提交一次 |
| 换行符警告 `LF will be replaced by CRLF` | Windows 换行 | 无害；可设 `git config --global core.autocrlf true` |
| 提交后发现漏了文件 | 忘记 `git add` | 补一个提交，不要 amend 已推送的提交 |
